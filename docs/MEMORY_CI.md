# Memory CI

Memory CI reviews the memory diff a pull request introduces. It compares the base revision's portable JSONL snapshot with the head revision's snapshot, publishes the diff, and fails the job when the pull request adds a new error trap.

The workflow lives at [`.github/workflows/fastr-memory-ci.yml`](../.github/workflows/fastr-memory-ci.yml). It is event-driven; no manual inputs are required.

## What the workflow does

1. Checks out the repository with full history so the base commit is available.
2. Installs root dependencies and builds the engine (`npm ci --ignore-scripts`, `npm run build:core`).
3. Reads `.fastr/memory.jsonl` from the head revision.
4. Materializes the base snapshot from `github.event.pull_request.base.sha`.
5. Runs `node dist/bin/fastr.js memory-ci --base <base> --head <head> --comment memory-ci.md --fail-on-new-traps`.
6. Writes `memory-ci.md` to the job summary.
7. Posts the diff as one PR comment, or updates the existing comment on a re-run.
8. Fails the job if the run added a new `error_trap` memory.

## Inputs

| Input | Source | Required | Notes |
|---|---|---|---|
| Head snapshot | `.fastr/memory.jsonl` in the pull request checkout | Yes | If the file is missing, the workflow logs a skip and creates no comment. |
| Base snapshot | `git show <base-sha>:.fastr/memory.jsonl` | No | If the base revision has no snapshot, the workflow compares the head against itself and reports a zero diff. |
| Base revision | `github.event.pull_request.base.sha` | Yes | Provided by the `pull_request` event. |
| New-trap gate | `--fail-on-new-traps` | Fixed in the workflow | Any added `error_trap` makes the job fail after the summary and comment steps. |
| Output path | `--comment memory-ci.md` | Fixed in the workflow | The file is also appended to `$GITHUB_STEP_SUMMARY`. |

The workflow does not accept `workflow_dispatch` inputs, secrets, or a database path. It reads the portable JSONL snapshot, not `.fastr/fastr.db` or its WAL files.

## Outputs

- **`memory-ci.md`** — Markdown diff generated by `formatDiffMarkdown`: from/to timestamps, token delta, added, superseded, still active, changed, open conflicts, and new error-trap ids.
- **Job summary** — the same Markdown, appended to the GitHub Actions summary for every reader, including fork PRs.
- **One PR comment** — the Markdown prefixed with the marker `<!-- fastrmemory-memory-ci -->`. The marker is how a re-run finds and updates the existing comment instead of posting another one.
- **Exit status** — `0` when the diff has no new error trap; `1` after a new error trap is reported. A missing head snapshot skips the diff instead of failing the job.

## Permissions

```yaml
permissions:
  contents: read
  pull-requests: write
  issues: write
```

`contents: read` is enough to fetch the base snapshot and build the engine. `pull-requests: write` and `issues: write` let the token create or update the PR comment. The workflow never writes to the repository or to a project database.

## Fork behavior

Pull requests from forks receive a read-only `GITHUB_TOKEN`. The workflow guards the comment step with:

```yaml
github.event.pull_request.head.repo.full_name == github.repository
```

For a fork PR:

- the diff still runs;
- the job summary still contains the full Markdown;
- no PR comment is created or updated;
- no secret or write token is exposed to the fork.

For a same-repository PR, the first run creates one marked comment. A synchronize, reopen, or re-run lists the issue comments, finds the comment whose body contains the marker, and updates it in place.

## Sample comment

The following is an illustrative comment body. Values come from the generated diff.

```markdown
<!-- fastrmemory-memory-ci -->
## FastrMemory diff

**From:** 2026-01-04T00:00:00.000Z
**To:** 2026-01-04T00:00:00.000Z
**Token delta:** +29

### Added (2)
- [mem_ci_new] Use WAL plus busy timeout (db, rule)
- [mem_ci_trap] Do not hold a write transaction open (db, error_trap)

### Superseded (1)
- [mem_ci_old] Use WAL (db, rule)

### Still active (0)
_None._

### Changed (0)
_None._

### Open conflicts (0)
_None._

**New error traps:** mem_ci_trap
```

Because this example adds `mem_ci_trap`, the job reports the diff and then exits `1` at the final gate.

## Local reproduction

Build the engine and generate two snapshots:

```bash
npm run build:core
node dist/bin/fastr.js snapshot export base.jsonl
# Switch to the head revision or otherwise produce the head snapshot.
node dist/bin/fastr.js snapshot export head.jsonl
```

Run the same CLI path the workflow uses:

```bash
node dist/bin/fastr.js memory-ci \
  --base base.jsonl \
  --head head.jsonl \
  --comment memory-ci.md \
  --fail-on-new-traps
echo "exit=$?"
```

The deterministic replay and Memory CI fixture is also exercised by:

```bash
npm run verify:replay
npm test -- tests/memory-ci.test.ts
```

## Troubleshooting

| Symptom | Cause | Action |
|---|---|---|
| Job is green and no comment appears | `.fastr/memory.jsonl` is absent | Commit the portable snapshot, or accept the skip. |
| Diff is empty | The base revision has no snapshot, so the workflow compares head against itself | Commit a base snapshot or merge the change that introduces it. |
| Workflow runs but no comment on a fork PR | Read-only fork token | Use the job summary; this is intentional. |
| Two comments appear | An older comment was created without the marker | Delete the stale comment; subsequent runs update the marked comment. |
| Job fails after posting the diff | The PR added an `error_trap` | Review the trap, then either fix the change or explicitly change the gate. |
